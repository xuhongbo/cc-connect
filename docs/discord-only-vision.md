# Discord-only 重构愿景

## 背景

当前仓库的核心价值，在于把本地运行的智能编码代理桥接到聊天工具里，并尽量保留各家代理自己的 `CLI` 能力、会话机制与本地状态。

但当使用入口全部落在同一个聊天时间线中时，项目、会话、目录、模式、模型、权限状态会快速混杂。对于 `Discord` 这类天然具备服务器、频道、线程、论坛、标签和交互组件的产品而言，多平台通用抽象反而会限制最终体验。

因此，新的重构方向不再追求“所有平台都支持”，而是把产品彻底收束成一个 **Discord 原生的 AI 编码工作台**。

---

## 产品定义

新分支的目标是：

> 把当前仓库重构成一个面向 `Discord` 服务器的 AI 编码工作台，围绕“频道 = 项目、线程 = 会话、一个线程只绑定一个代理”的模型来组织全部交互。

这个定义包含 4 个不可动摇的约束：

1. **只做 Discord**
2. **线程是一等会话单位**
3. **一个线程只绑定一个代理**
4. **代理继续通过本地 CLI 驱动**

---

## 为什么只做 Discord

### 1. Discord 的空间模型更适合管理复杂开发流程

`Discord` 原生提供：

- 服务器
- 分类
- 项目频道
- 线程
- 论坛频道
- 标签
- 交互命令
- 按钮、下拉、弹窗

这使得它天然适合承载：

- 项目隔离
- 会话隔离
- 代理身份区分
- 会话归档与回看
- 可视化管理入口

### 2. 多平台兼容会不断稀释产品能力

一旦为了飞书、Telegram、Slack、QQ 等同时兼容，设计就会被迫回到：

- 最低公共能力
- 最弱交互模型
- 平台无感知核心抽象

这与重构目标冲突。

### 3. Discord 允许更贴近直觉的工作方式

我们希望用户的感受是：

- 在一个项目频道里看到这个项目的会话
- 每个会话在线程里独立推进
- 不同代理用前缀、标签、颜色明确区分

这比“所有东西混在一个聊天里”更接近真实工作流。

---

## 固定空间模型

新分支固定采用以下空间模型：

- **服务器** = 工作空间
- **频道** = 项目
- **线程** = 会话
- **一个线程** = **一个代理**

在同一个项目频道中，可以同时存在：

- `[Claude] 修复登录`
- `[Codex] 重构支付`
- `[Gemini] 调研缓存`

但每个线程只能绑定一个代理，不能让多个代理在同一线程中同时发言。

---

## 代理接入原则

新分支保留当前仓库最成熟的代理运行方式：

- `Claude Code`：直接调用本地 `claude`
- `Codex`：直接调用本地 `codex`
- `Gemini CLI`：直接调用本地 `gemini`

不做：

- 统一云端模型网关
- 自建一层假的通用模型运行时
- 把各家 `CLI` 行为抹平

原因很简单：当前仓库已经证明，各家代理的会话模型、恢复方式、附件处理和运行方式并不相同。保留差异，反而更稳。

---

## 第一阶段的产品边界

第一阶段只做最核心闭环，确保“项目频道 → 单代理线程 → 本地 CLI 会话”可以长期稳定跑通。

### 第一阶段必须具备

- `Discord` 项目频道与线程工作流
- `Claude` / `Codex` / `Gemini`
- 文本、图片、文件输入
- 流式输出
- 会话恢复
- 基础状态持久化
- 基础项目、会话、代理命令
- 代理身份的前缀、标签、颜色展示

### 第一阶段明确不做

- 语音输入输出
- 定时任务
- 心跳巡检
- 多机器人中继
- 管理后台
- 多平台兼容
- 复杂权限系统

---

## 长期产品方向

长期看，这个产品会沿着 4 个阶段演进：

1. **核心闭环**：先做稳项目频道、线程、代理会话与恢复
2. **管理增强**：项目面板、线程发现、项目目录与状态管理
3. **自动化**：定时任务、巡检、提醒与恢复工具
4. **管理界面**：可视化状态、外部管理能力与运维工具

但无论扩展到哪一步，都不回头做多平台通用桥接器。

---

## 明确放弃的方向

新分支明确放弃以下目标：

- 多平台统一抽象
- 继续扩张飞书、Telegram、Slack 等能力
- 为跨平台兼容牺牲 Discord 原生体验
- 把 `Discord` 降级成“只是一个平台适配器”

---

## 成功标准

当这个分支真正成型时，应该满足：

1. 用户可以把一个频道理解成一个项目空间
2. 用户可以把一个线程理解成一个独立工作会话
3. 用户能一眼看出当前线程绑定的是哪个代理
4. 服务重启后，线程与代理会话关系不会丢
5. 新增能力始终围绕 Discord 空间模型演进，而不是回到通用桥接思路
