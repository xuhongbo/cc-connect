# agentcord 对比与决策记录

## 目的

这份文档记录 `agentcord` 与当前 Discord-only 重构方向之间的关系，明确：

- 哪些地方值得借鉴
- 哪些地方不能照搬
- 为什么第一期仍然坚持现有 `CLI` 路线

同时，仓库中已保留一份参考代码副本：

```text
references/agentcord/
```

该目录仅用于研究和按需借鉴，不代表目标架构本身。

---

## 参考仓库概览

参考仓库：

- 上游地址：`https://github.com/radu2lupu/agentcord`
- 本地参考副本：`references/agentcord/`

本地查看后可以确认：

- 使用 `Node`
- 使用 `discord.js`
- 使用 `@anthropic-ai/claude-agent-sdk`
- 可选使用 `@openai/codex-sdk`
- 用“项目分类 + 会话频道”的方式管理 Discord 空间

---

## 相似点

`agentcord` 与本项目目标相似之处在于：

1. 都是 **Discord + 本地代理工作流**
2. 都强调 **会话持久化**
3. 都强调 **流式回复**
4. 都有 **项目级组织**
5. 都把 `Node + Discord.js` 作为可行技术路线

这些相似点说明：

> 我们选用 `Node + Discord.js` 来做 Discord-only 重构，是一条被实际项目验证过的可行路线。

---

## 最大差异：空间模型

### agentcord

核心模型更接近：

- **分类** = 项目
- **文本频道** = 会话

### 我们的目标

固定模型是：

- **频道** = 项目
- **线程** = 会话
- **一个线程** = **一个代理**

### 决策

必须坚持我们的模型，不能被参考仓库带回“频道 = 会话”的模式。

原因：

1. 频道级会话在会话数增多时会迅速膨胀
2. 我们已经确认“项目频道统一入口 + 线程承载会话”更符合直觉
3. 线程模型更适合在单项目空间内并行推进多个任务

---

## 代理接入方式对比

### agentcord

- `Claude`：使用 `@anthropic-ai/claude-agent-sdk`
- `Codex`：使用 `@openai/codex-sdk`
- 倾向通过 SDK 拿结构化事件

### 我们当前目标

第一期继续沿用当前仓库最成熟的策略：

- `Claude` → 本地 `claude`
- `Codex` → 本地 `codex`
- `Gemini` → 本地 `gemini`

即：

> 继续以本地 `CLI` 为中心，而不是立刻切到 SDK 为中心。

### 决策

第一期**不**因为参考仓库而改成 SDK 优先路线。

原因：

1. 当前仓库已有 `CLI` 适配经验，迁移成本最低
2. `Claude` / `Codex` / `Gemini` 三者可以保持一致心智
3. 第一阶段最重要的是验证线程工作台模型，而不是重写代理运行层
4. 如果一开始就混入 SDK，会扩大第一阶段风险面

---

## 关于“官方 SDK”的澄清

### Discord 层

`agentcord` 使用的是：

- `discord.js`

这不是 Discord 官方机器人 SDK。

Discord 官方文档当前明确说明：

> Discord does not maintain official SDKs.

因此，对我们的 Discord 机器人开发来说，`discord.js` 依然是社区主流方案，而不是官方机器人 SDK。

### 代理层

`agentcord` 的“官方”主要体现在代理层：

- `Claude` 官方代理 SDK
- `Codex` 官方 SDK

这说明 SDK 方案在后续可以研究，但不改变第一期决策。

## 可借鉴点

以下部分值得重点学习和按需吸收：

### 1. Discord.js 工程组织

可借鉴：

- 命令注册
- 交互处理分层
- `discord.js` 模块划分

### 2. 流式消息编辑模式

可借鉴：

- 一条消息持续编辑
- 节流刷新
- 停止按钮
- 组件式输出控制

### 3. 会话持久化意识

可借鉴：

- `sessions.json`
- `projects.json`
- 重启恢复思路
- 孤儿会话清理/同步意识

### 4. 代理事件翻译层

可借鉴：

- 将代理输出事件翻译成统一上层事件
- 再交给 Discord UI 层渲染

### 5. 项目级配置思路

可借鉴：

- 项目级个性化配置
- 技能与项目配置挂载方式

但这些内容不应该在第一阶段全部照搬。

---

## 不采用的部分

以下部分明确不作为目标架构：

### 1. 分类 = 项目、频道 = 会话

原因：

- 与目标空间模型冲突
- 会导致会话多时频道爆炸

### 2. tmux 作为核心会话原语

原因：

- 增加额外会话层复杂度
- 与我们“线程 ↔ 代理会话绑定”的主模型不一致
- 第一阶段没有必要引入

### 3. 立刻全面转向 SDK

原因：

- 会扩大实现风险
- 会破坏三代理统一的第一阶段心智
- 会把重点从线程工作台模型转移到运行层重写

---

## 第一阶段决策结论

第一阶段固定采用：

- `Discord.js`
- 频道 = 项目
- 线程 = 会话
- 一个线程 = 一个代理
- `Claude` / `Codex` / `Gemini` 继续走本地 `CLI`

并明确吸收以下经验：

- 流式编辑消息
- 更清晰的交互组件组织
- 更强的持久化意识
- 代理事件翻译层设计

---

## 第二阶段以后可重新评估的事项

以下事项不是现在做，但可以在后续阶段再次评估：

1. `Claude` 是否引入官方 SDK 作为可选后端
2. `Codex` 是否引入官方 SDK 作为可选后端
3. 是否形成 `CLI / SDK` 双运行实现
4. 是否引入终端接管能力作为调试能力，而非核心架构

---

## 使用方式

后续任何实现计划如果引用 `references/agentcord/`，都应该先回答两个问题：

1. 这次借鉴的是“实现技巧”，还是“产品模型”？
2. 这次借鉴会不会把我们带回频道会话模型、tmux 核心模型或 SDK 优先模型？

如果答案会偏离本项目目标，则应拒绝照搬。
