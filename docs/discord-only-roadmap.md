# Discord-only 路线图

## 总原则

路线图遵循 4 条原则：

1. **先闭环，再扩展**
2. **先可管理，再自动化**
3. **先 Discord 原生体验，再外围工具**
4. **不回头做多平台抽象**

---

## Phase 1：核心闭环

### 目标

把以下链路做稳：

> 项目频道 → 单代理线程 → 本地 CLI 会话 → 流式回复 → 重启后恢复

### 范围

- Discord-only
- `Claude` / `Codex` / `Gemini`
- 文本、图片、文件
- 流式输出
- 基础持久化
- 基础恢复
- 基础项目/会话/代理命令
- 代理标签、前缀、颜色

### 不做

- 语音
- 定时任务
- 心跳
- 中继
- 管理后台
- 复杂权限系统

### 完成定义

- 项目频道可创建三类代理线程
- 线程可稳定对话
- 线程与代理绑定可恢复
- 错误、取消、重试、重开链路可用

### 当前实施提醒

当前仓库中的 `discord-app/` 只允许向这个阶段继续推进。

- 允许补强一期闭环内的测试、恢复、流式更新与附件处理
- 不允许顺手加入管理面板、自动化、后台接口等二期/三期能力
- 若发现需求超出这一节范围，应把它移回后续阶段处理

---

## Phase 2：管理增强

### 目标

提升“一个项目频道里有很多线程”时的可管理性。

### 范围

- 项目频道管理面板
- 活跃线程列表
- 最近线程列表
- 错误线程可见性
- 线程标签管理增强
- 项目默认代理与目录控制
- 模型/模式展示增强

### 重点产物

- 项目置顶状态消息
- 更清晰的线程发现入口
- 更明确的项目当前目录与代理默认值

### 完成定义

- 项目频道不靠人工翻聊天记录也能找到关键线程
- 项目当前状态可视化
- 默认代理和目录可以被可靠管理

---

## Phase 3：自动化与续航

### 目标

让 Discord 工作台不只是“聊天驱动”，而能承载持续性任务。

### 范围

- 定时任务
- 巡检/心跳
- 完成通知
- 失败提醒
- 恢复失败视图
- 项目健康检查

### 完成定义

- 能从 Discord 中发起自动化任务
- 自动化任务状态对用户可见
- 线程、项目、代理的异常能被主动发现和提醒

---

## Phase 4：管理界面与扩展能力

### 目标

围绕 Discord 工作台补充更强的运维与可视化能力。

### 范围

- Web 管理面板
- 外部管理接口
- 会话统计
- 错误统计
- 可视化项目/线程/代理健康状态
- 导出与搜索能力

### 完成定义

- 项目维护者不必只靠 Discord 线程回看状态
- 运维与恢复不再全靠命令完成

---

## 长期保留但后置的能力

以下方向不是当前优先级，但架构上不能堵死：

- 新增更多本地代理
- 更复杂的权限体系
- 更强的项目目录管理
- 更丰富的自动化编排

---

## 明确不回头的事情

以下方向在新分支中默认视为不再继续：

- 多平台统一抽象
- 为飞书、Telegram、Slack 等重新设计通用能力
- 以最低公共能力为中心做产品决策

---

## 路线图使用方式

后续所有计划文档都必须明确标注自己属于哪个阶段，并说明：

- 本次实现覆盖哪个阶段目标
- 哪些能力仍然故意留到后续阶段
- 有没有不小心侵入了后续阶段范围

只有这样，才能避免第一阶段边做边膨胀。

当前第一阶段实施计划见：

- `docs/plans/2026-03-25-discord-only-phase1-implementation-plan.md`
